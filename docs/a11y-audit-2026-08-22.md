# Accessibility audit — this session's UI additions (2026-08-22)

Scope: every component added this session — Admin → Execution (RPC/signer/
mint-plan forms and tables, passkey registration, arm/disarm controls, the
browser-wallet sign prompt, the project picker), the Minting Calendar, and
the feed table's new concentration badge. Static code review against
WCAG 2.2 AA and this repo's own DESIGN.md accessibility section — **no
running browser/dev server in this environment**, so this is not a
substitute for a live keyboard-and-screen-reader pass; flagged, not hidden.

## Found and fixed

| Issue | WCAG | Where | Fix |
|---|---|---|---|
| "Project" label was a bare `<span>` sibling, not associated with its input at all — every other form in this codebase correctly wraps the label | 1.3.1, 3.3.2 | `project-picker.tsx` | Wrapped in `<label>`, matching the project's own established pattern exactly |
| Search results list had no combobox semantics — no `aria-expanded`/`role`, so a screen reader user gets no indication results appeared | 4.1.2 | `project-picker.tsx` | Added `role="combobox"` + `aria-expanded`/`aria-controls`/`aria-autocomplete` on the input, `role="listbox"`/`role="option"` on the results (switched `<ul>`/`<li>` to `<div>`/`<button>` — Biome's own a11y lint rejects an interactive ARIA role on a semantically non-interactive `<ul>`, which is also the more common accepted pattern for this exact widget) |
| "No matches yet" appeared with no announcement to screen reader users watching a live search | 4.1.3 | `project-picker.tsx` | `aria-live="polite"` region |
| Arm result message had no `role="status"`/`"alert"` — every other result message in this codebase has one; this one silently didn't | 4.1.3 | `mint-plan-controls.tsx` (`ArmControls`) | Added the same `role={ok ? "status" : "alert"}` pattern used everywhere else |
| Four new admin tables (RPC endpoints, Signers, Mint plans, Execution history) had `<th>` with no `scope="col"` — `feed-table.tsx` already does this correctly, these four didn't | 1.3.1 | `admin/execution/page.tsx` | `scope="col"` on every header, `sr-only` label on the trailing actions-only column header |
| Calendar's per-day tables had **no `<thead>` at all** — zero column context for screen reader users | 1.3.1 | `calendar/page.tsx` | Added a `sr-only` `<caption>` + `<thead>` with `scope="col"` headers — visually invisible, so the departure-board density is unchanged |

All fixes verified via `pnpm --filter @hoodmint/web run typecheck`, `pnpm run lint` (Biome's own `a11y` rule set caught the `<ul role="listbox">` issue — confirming the review, not just asserting it), `format:check`, and a production `next build`, all clean.

## Checked and already correct

- Color is never the only status signal anywhere added this session — every
  status/health/severity indicator (RPC health, signer status, mint-plan
  status, execution-attempt status, the concentration badge, the
  shadow-mode/ENABLED indicator) pairs color with a visible text label,
  consistent with DESIGN.md's rule.
- Every button has an accessible name via visible text content; the one
  icon-adjacent control (`ArmControls`'s minutes input) has an explicit
  `aria-label`.
- No positive `tabindex` anywhere; no custom keyboard traps introduced.
- Every interactive element added is a real `<button>`/`<a>`/`<input>` —
  no `<div onClick>` pattern anywhere in this session's additions.
- Heading hierarchy is correct everywhere: Admin → Execution's `<h2>`s
  nest under the layout's own `<h1>`; the Calendar page has its own `<h1>`
  with `<h2>` day-group headers under it — no skipped levels.

## Not verified, and why

- **Live contrast measurement in both themes.** DESIGN.md's token map
  (`amber`/`magenta`/`acid`/`cyan`) is used exactly as documented and
  already passes AA per the design system's own stated guarantee — but
  this session did not re-measure computed contrast against a rendered
  page, since no browser/dev server exists here.
- **Real keyboard/screen-reader walkthrough.** The `ProjectPicker`
  specifically deserves one: Tab reaches every result button (native
  focusability), but full arrow-key combobox navigation (up/down through
  results without leaving the input) was not implemented — a reasonable
  middle ground given the constraint, not a full ARIA 1.2 combobox
  pattern. Flagging rather than claiming completeness.
- **Touch target sizing (2.5.8, ≥24×24px).** Several controls added this
  session (`px-2 py-0.5 text-[11px]` row actions, the RSS link) are likely
  under 24px tall. This matches the *exact* sizing convention already used
  throughout the entire existing admin console (every pre-existing row
  action — `ProviderToggle`, wallet-form buttons, etc. — uses identical
  sizing) — this is a systemic, project-wide characteristic of the
  "operator-dense" design language (DESIGN.md), not something unique to
  this session's additions. Fixing it in isolation on only the new
  components would create visual inconsistency without fixing the
  underlying pattern; it needs its own dedicated design-system pass across
  the whole admin console, not a one-off patch here.

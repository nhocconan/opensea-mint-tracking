# 0004 — Execution custody model: EIP-7702 + Safe/Zodiac Roles Modifier primary (with mandatory recipient-parameter pinning and two-tier caps), minimal custom Executor contract fallback

Date: 2026-08-21
Status: accepted
Produced by: multi-agent expert panel (CTO/CPO orchestration, `/goal`) — see
[`docs/execution-architecture.md`](../execution-architecture.md) for the full
roadmap this ADR is one piece of, and the panel's underlying position papers.

## Context

Three panelists proposed three different primary custody patterns: the Blockchain Security lane recommended EIP-7702 delegating the Ledger EOA to Safe's implementation with a session-key/allowance module; the Risk/SRE lane recommended Safe + Zodiac Roles Modifier (function-selector- and contract-scoped, on-chain-enforced caps, audited, in production for DAO treasuries today) without committing to 7702 as the delivery mechanism; the CTO/Systems lane recommended ERC-4337 session-key smart accounts as the general default, explicitly because they work uniformly across any EVM chain without needing 7702 support. This is a real conflict, not just phrasing: 4337-without-7702 requires deploying a fresh smart-account address, which silently invalidates OpenSea allowlist stages that are frequently pre-snapshotted Merkle proofs keyed to the exact EOA address — a concrete, drop-breaking problem the other two lanes flagged and the CTO lane did not address. A subsequent red-team pass on the first version of this ADR found two further holes that would have shipped as false safety: (1) selector + target-contract + value/gas/day caps alone do not scope the *calldata parameters* of an allowlisted call — a compromised apps/executor host could call the allowlisted mint selector, within every cap, but pass an attacker's address as the `to`/`recipient` argument and steal the NFT while every dollar-figure guardrail holds; the ADR had this control specified for the fallback Executor contract but not for the primary Safe/Zodiac path that will actually hold real funds first. (2) 'On-chain value/gas/day caps' and 'one spend ceiling per arm' were asserted without saying whether the per-arm number the owner types into the UI is itself pushed on-chain (which would mean a Ledger tap per arm, contradicting 'Ledger tapped only for chain-onboarding and permission changes') or is enforced only in application/DB state (which would make the specific per-arm ceiling only as strong as a policy-check bug or DB tampering on a compromised host — reintroducing exactly the multi-path signing risk ADR 0005's single chokepoint was designed to prevent, just for spend precision instead of signing). Neither gap is cosmetic: both let every named guardrail hold true while the actual asset at risk (the NFT, or the precise intended spend) is not actually protected.

## Decision

PRIMARY, everywhere it verifies as available: a chain-scoped EIP-7702 authorization (chain_id pinned per target chain, never chain_id=0 — one deliberate Ledger tap per chain, not per mint) delegating the Ledger EOA to Safe's 7702-compatible implementation, with a Zodiac Roles Modifier scoping the hot session key to specific function selectors (mint/claim) on specific allowlisted contract addresses, with on-chain value/gas/day caps AND mandatory per-parameter (EqualTo) calldata scoping on every recipient-shaped parameter (to/recipient/receiver/account — whatever the target ABI names it) pinned to the Safe's own address. No allowlist entry may ship without this parameter scope. A mint function whose ABI has no cleanly scopable recipient parameter (e.g. the recipient is buried inside an opaque merkle-proof struct rather than a plain address argument) is out of scope for the Roles path entirely and routes through the custom Executor contract fallback instead. Allowlisting is per-collection and never batched: adding a contract address to the Roles Modifier — and simultaneously setting or updating that collection's standing on-chain spend ceiling (see cap tiering below) — is its own individually Ledger-signed transaction, reviewed by the owner against the actual contract address at that moment; this doubles as the real phishing/clone-collection checkpoint, not merely a permission grant. The hot session key is a non-owner Roles-scoped signer, never a Safe owner. Session-key material is sealed via the existing packages/secrets AES-256-GCM primitive, in its own credential type/table distinct from the OpenSea PAT, decrypted per-signature (never cached in a long-lived signer instance), with the existing redaction list extended to cover privateKey/sessionKey field names.

Cap tiering, stated explicitly: the on-chain Roles Modifier value/gas/day cap set at allowlist time is a COARSE, CONSERVATIVE BACKSTOP — the most the owner is willing to see spent against that collection between Ledger taps, sized to the largest single plan the owner expects for that collection. Because the recipient-pinning control above already prevents fund diversion, this backstop exists to bound accidental double-spend, replay, or overlapping-plan exposure, not theft. The PER-ARM ceiling the owner sets in the UI for one specific plan is the precise, day-to-day number: it is strictly ≤ the collection's on-chain coarse cap, is stored on the mintPlans row, and is enforced by packages/core's pure policy check as part of the same atomic armed→executing transition (ADR 0005) — never by a separate, later, or best-effort check. Both numbers are real caps at different layers (on-chain = hard worst-case ceiling that survives a fully compromised app/DB; app-level = precise per-plan intent); neither is described as 'the' cap and neither substitutes for the other. Once caps are ever raised beyond the initial smallest-meaningful-cap phase, value/day caps use a rolling 24h window, not a calendar-day boundary, so a near-midnight pair of mints cannot approach 2x the intended daily exposure.

FALLBACK, only for a target chain/contract where 7702+Safe/Zodiac isn't verified-available (name Robinhood Chain explicitly — it is roughly five weeks old at time of writing and Safe/Zodiac deployment there is unconfirmed), a target contract's mint ABI has no recipient parameter routable through Safe cheaply, OR the recipient can't be cleanly parameter-scoped per above: a minimal, purpose-built, immutable Executor contract with a single executeMint(target, calldata, value) entrypoint, hardcoded so any decoded recipient/`to` in the allowlisted calldata shape must equal the Ledger address or the call reverts, with a per-target allowlist only the Ledger can update, under the same per-collection, individually-reviewed, non-batched discipline as the primary path.

## Consequences

Requires two build-time verifications before Phase 2 starts: (a) Ledger's clear-signing whitelist currently includes the chosen Safe 7702-delegate contract address, and the exact expected Ledger-screen contents are documented in a runbook the owner can visually check before tapping; (b) Safe + Zodiac Roles Modifier's audited-deployment status specifically on Robinhood Chain, which decides whether the primary or fallback path is used there on day one. A required merge gate for every new collection allowlist entry, on either the primary or fallback path: a Roles-Modifier (or Executor) integration test that attempts to redirect the mint recipient to a non-Safe/non-Ledger address and asserts a revert — this is the concrete artifact proving the recipient-pinning control actually holds on-chain, not just in ADR prose, and it is not optional polish. Introduces packages/signing as the single package in the system allowed to decrypt spend-capable key material. Ruling downgrades the CTO lane's ERC-4337-without-7702 proposal from 'general default' to a narrower fallback role: acceptable only for a future chain where 7702 isn't live, AND the specific target drop's allowlist is verified not to be address-snapshotted (checked per drop) — otherwise the fallback is the custom Executor contract, not a fresh 4337 account.

## Alternatives rejected

Raw unconstrained hot EOA with only app-level checks — rejected, unbounded blast radius, nothing on-chain stops a compromised worker from calling anything else with that key. Fresh ERC-4337 smart account without 7702 as the general default — rejected for the address-migration/allowlist-invalidation reason above; retained only as the narrow fallback described. Third-party custodial/MPC signer (Fireblocks, Turnkey) — real, audited option with a genuine policy engine, rejected as the default because it adds a recurring-cost third-party vendor and a new ToS surface that's in tension with a self-hosted, single-operator system trying to minimize trust surfaces; kept as a documented escalation path only if spend caps are later raised materially. Uniform bulk/batch allowlisting of multiple collections behind a single Ledger tap — rejected; it would remove the one moment a human actually looks at the target contract address, trading a minor convenience for a real clone-contract/phishing blind spot. Enforcing the per-arm ceiling purely on-chain via a Ledger tap at arm time — rejected as the general mechanism; it would mean a physical tap every time the owner arms a plan, which does not scale to 'personal assistant tracking many drops' and contradicts the stated Ledger-tap-frequency design goal, so the coarse/precise two-tier split above is used instead.

## Amendment (2026-08-21, post-panel verification): prefer OpenSea's own mint API as the calldata source for OpenSea-hosted drops

The panel did not have this fact — it was independently verified against `docs.opensea.io` after the panel ran, and it materially improves this ADR's execution path for the specific case of OpenSea-hosted SeaDrop drops (most of what the owner cares about).

**Finding.** OpenSea now documents an official programmatic mint path: `POST /api/v2/drops/{collection-slug}/mint` (and the SDK's `buildDropMintTransaction(collectionSlug, { minter, quantity })`), which takes a `minter` address and returns ready-to-broadcast `{ target, calldata, value }`. Separately, OpenSea's "Build with AI Agents" docs list minting and SeaDrop deployment among 30+ tools exposed by an official MCP server (`mcp.opensea.io`), and an instant-key endpoint this repo already uses for read scopes (`POST /api/v2/auth/keys`, 600/h read · 30/h write · 7-day expiry) covers write scope too.

**Why this matters for ADR 0004.** `minter` is a parameter distinct from whoever signs and broadcasts the transaction — i.e., OpenSea's own SeaDrop design already supports "someone else pays gas, a different address receives the mint," which is exactly the shape a Zodiac-Roles-scoped session key needs. For SeaDrop drops specifically, this removes most of the per-contract ABI uncertainty flagged in `needs_verification` (recipient parameter presence, merkle-proof argument shape): OpenSea computes the calldata server-side, already accounting for the correct stage/proof, so the MintAdapter for "OpenSea-hosted SeaDrop drop" only needs to (a) call this endpoint with `minter` = the Roles-Modifier-pinned Safe address, (b) run the mandatory pre-flight simulation (ADR 0005) against the *returned* `target`/`calldata`, then (c) route it through the same Zodiac per-parameter recipient-pinning check as any other allowlisted call — the recipient pin is checked against OpenSea's own returned calldata, not trusted blindly. Non-SeaDrop / non-OpenSea-hosted mints still need the general per-contract ABI verification this ADR already requires.

**Effect on the ToS open risk (see `docs/execution-architecture.md`).** This does not resolve the open ToS question — OpenSea's Terms of Service themselves still contain no clause this panel or this verification pass could find that explicitly covers "operator's own bot minting to their own wallet." But an OpenSea-documented, OpenSea-hosted API with an official AI-agent integration story is meaningfully stronger evidence of sanctioned use than a bare direct-RPC contract call would have been, and it should be weighed by the owner as part of that same explicit, eyes-open acceptance gate before Phase 2's real-money gate opens — not treated as a green light on its own.

**Decision update.** Add "prefer OpenSea's official mint API over hand-rolled SeaDrop calldata whenever the target drop is OpenSea-hosted" to this ADR's decision. Everything else in this ADR (EIP-7702 + Safe/Zodiac primary, custom-Executor fallback, recipient-parameter pinning, two-tier caps, per-collection non-batched allowlisting) is unchanged.

## Amendment (2026-08-22, Phase 2 implementation pass): the PRIMARY path's own required build-time verification (a) fails — Ledger cannot sign the Safe delegation today. Executor fallback promoted to the actual build target.

This ADR's own "Consequences" section named two build-time verifications required before Phase 2 starts. Both were checked live this pass, against primary sources, not memory:

**(b) checked, passes:** Safe *is* genuinely deployed on Robinhood Chain (4663) — not merely "canonical" in `safe-deployments`' addressing scheme, but confirmed via a direct `eth_getCode` call against the chain's production RPC returning real, non-empty bytecode at the canonical SafeL2 v1.4.1 singleton address (`0x29fcB43b46531BcA003ddC8FCB67FFE91900C762`). EIP-7702 itself is very likely live on Robinhood Chain too — it's an Arbitrum Orbit chain, ArbOS 40 ("Callisto," Arbitrum's Pectra-equivalent upgrade shipping 7702 support) predates Robinhood Chain's July 1 2026 mainnet launch, so any Orbit chain launched after that inherits it — though this second fact is inference from Arbitrum's release cadence, not an independent on-chain confirmation the way (b)'s Safe check was.

**(a) checked, FAILS:** "Ledger's clear-signing whitelist currently includes the chosen Safe 7702-delegate contract address" — false, as of this pass. Ledger's own developer documentation states EIP-7702 delegation-target whitelisting is enforced **at the device firmware level**, and today it covers *only* the Ethereum Foundation's simple reference delegate contract — explicitly not Safe's implementation, with Ledger's own stated caution that they'll only consider whitelisting additional (more complex) delegate contracts "after careful consideration of the security risks," with no committed timeline. This is not a UI warning or a wallet-software gap that a different frontend could route around — it is the hardware device itself refusing to produce a signature for a 7702 authorization pointing anywhere but the EF contract. No amount of correct application code on this project's side changes that.

**Consequence.** The PRIMARY path this ADR specifies (Ledger EOA → EIP-7702 → Safe implementation → Zodiac Roles Modifier) cannot be built for real use today, full stop — not because Robinhood Chain lacks the infrastructure (it doesn't lack it; (b) passed), but because the one device the owner actually owns cannot produce the one signature the whole path starts from. This reverses which path is "the real one to build": the custom Executor contract, specified in this ADR as the FALLBACK for exactly the condition "a target chain/contract where 7702+Safe/Zodiac isn't verified-available," is promoted to the actual Phase 2 build target — not because this ADR's chain-level reasoning was wrong, but because a *device*-level constraint the panel didn't have visibility into (Ledger's own firmware whitelist policy, dated after this ADR) makes the primary path's required first step unusable regardless of chain readiness.

**Scope note on the Executor's on-chain caps.** This ADR's cap-tiering language ("on-chain value/gas/day caps") is implemented for the Executor fallback as an on-chain **value** cap over a rolling 24h window (per this ADR's own rolling-window requirement) plus the existing mandatory pre-flight simulation (ADR 0005) as the practical gas-cost bound — not a separate on-chain gas-metering mechanism. Gas cost is a property of the specific call being executed and isn't reliably capped by a static on-chain check without either an unreliable heuristic or `gasleft()`-based tricks that break composability with the target mint contract's own gas needs; the simulation step already run before every broadcast (never bypassable, ADR 0005) is judged the correct place to catch a gas anomaly, consistent with how gas is already handled for the `browser_wallet` scheme today. Documented here as a deliberate scope decision, not a silent gap.

**This does not touch the recipient-pinning control**, which is the ADR's actual theft-prevention mechanism and was already specified for the Executor contract in the original decision text: `executeMint`'s hardcoded requirement that any decoded recipient in the allowlisted calldata shape equal the Ledger's own address, or revert. That requirement, and the required merge-gate integration test proving it holds (attempt to redirect the mint recipient to a non-Ledger address, assert revert), are unchanged and are what's actually implemented and tested in `contracts/`.

**Left in place, not deleted:** the EIP-7702 + Safe/Zodiac Roles Modifier code path remains this ADR's stated eventual primary — worth revisiting the moment Ledger's firmware whitelist is extended to cover Safe (or the owner adopts a signer whose firmware already supports it), since Zodiac's per-parameter calldata scoping is a strictly finer-grained control than this project's own hand-rolled Executor contract can offer without becoming Zodiac itself. `packages/db`'s `signers.scheme` enum already carries `eip7702_safe_zodiac` for exactly this reason — nothing about this amendment removes that option, it only says which path gets real code and real Ledger-signed transactions in this pass.

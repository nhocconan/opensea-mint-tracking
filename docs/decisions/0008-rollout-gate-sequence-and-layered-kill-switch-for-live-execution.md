# 0008 — Rollout gate sequence and layered kill switch for live execution

Date: 2026-08-21
Status: accepted
Produced by: multi-agent expert panel (CTO/CPO orchestration, `/goal`) — see
[`docs/execution-architecture.md`](../execution-architecture.md) for the full
roadmap this ADR is one piece of, and the panel's underlying position papers.

## Context

The Risk/SRE lane proposed a 5-gate table (shadow → testnet rehearsal → single capped mainnet mint → bounded scale-up → continuous drill) with concrete exit criteria including deliberately injected failures. The CPO lane proposed a compatible 3-phase sequence (Evaluate-only → Rehearsal → First real mint) with concrete product-surface requirements (scoped arm/disarm UX, step-up auth, Telegram kill switch). These are not in conflict and are merged below into one sequence with the custody decision from ADR 0004. A red-team pass on the first version of this ADR found two further gaps: 'Better Auth step-up re-authentication' was left unspecified as a mechanism even though arming is the sole software gate standing in front of the on-chain caps, and the layer-1 on-chain kill switch's 'phone-executable' claim was asserted without naming or verifying the actual Ledger hardware model and its phone-only signing path — a USB-only Ledger cannot sign from a phone at all, which would silently break the one disaster-recovery layer designed to survive 'the owner is asleep and the server is unreachable.'

## Decision

Adopt the 4-phase roadmap (Phase 0 foundation → Phase 1 zero-custody execution scaffolding → Phase 2 delegated real broadcast → Phase 3 deliberate broadening) with the Risk/SRE lane's exit criteria as the literal gate conditions between phases, and the CPO lane's arm/disarm UX rules as the product surface enforcing those gates: every arm is scoped to exactly one collection + one execution wallet + one spend ceiling + one time window, requires Better Auth step-up re-authentication, and auto-disarms at window close (enforced by ADR 0005's atomic condition, not a best-effort job) — no global 'arm everything' state exists as a feature, in any phase. Step-up re-authentication for arming is specifically WebAuthn/hardware-security-key-bound (a phishing-resistant factor — e.g. a platform passkey or a FIDO2 key), not a password or TOTP re-prompt, since a phished software gate would sit directly in front of the on-chain caps.

The kill switch is layered by independence, strongest first: (1) an on-chain Ledger-signed Roles-Modifier revoke, executable from any block explorer's write-contract UI, independent of whether this codebase, the server, or the network is reachable at all. This layer's 'phone-executable' claim is verified once against the owner's actual Ledger hardware before Phase 2's real-money gate opens: the specific device model and its phone-only signing path (e.g. a Bluetooth-capable Nano X/Stax/Flex paired to Ledger Live mobile, or a WalletConnect session from Ledger Live mobile into a block explorer's write-contract page) is named in the runbook and physically rehearsed from a phone with no laptop present during the first kill-switch drill. If the owner's actual unit is USB-only, this is treated as a blocking gap: either the owner acquires a phone-capable device before Phase 2, or the runbook is rewritten to state honestly that layer 1 requires a laptop/OTG cable and the disaster-recovery story is adjusted accordingly — the claim is never left as an unverified assumption. This is the true disaster-recovery layer and gets a one-page phone-executable runbook. (2) docker stop/systemctl stop of the apps/executor container via SSH, independent of web/DB health. (3) a polled Postgres flag as the fast (~5–10s) routine-operations pause, not the disaster path. Every execution attempt, success or failure, fires an immediate Telegram alert via the existing notification_outbox infra with its own alertType, never batched or deduped the way routine drop alerts are.

## Consequences

No cap increase happens without a reviewed, complete audit trail (Execution History, first-class nav item, immutable rows, shipped in Phase 1 before any real signing) and explicit owner action — never an automatic timeout back to a higher cap. A kill-switch drill, including the on-chain revoke path rehearsed from a phone, becomes a standing monthly operational task and is re-run after any refactor of the execution path; the same drill also exercises the recipient-redirect revert test (ADR 0004) and the expired-arm-cannot-fire test (ADR 0005) so the safety rails are proven together, not just individually unit-tested. Phase 2's real-money gate cannot open until the OpenSea ToS question (ADR/open-risk, unresolved by two independent panelists) has been read by the owner and knowingly accepted, not silently absorbed. WebAuthn step-up means the owner needs a registered passkey/hardware key set up before Phase 1's arm UI is usable at all — a small but real new setup dependency, called out explicitly rather than discovered mid-build.

## Alternatives rejected

Time-based automatic cap increases — rejected, removes the human checkpoint that makes 'the owner is asleep' survivable. A single kill-switch layer (app-level flag only) — rejected, shares fate with the exact infrastructure (DB, server) that might be the thing failing or compromised. Password/TOTP step-up re-auth — rejected as the arming gate specifically because it is the last software checkpoint before on-chain caps take over, and phishable factors are a poor fit for that position even though they're adequate for read-only admin actions elsewhere in the app.
